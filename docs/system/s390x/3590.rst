Emulated 3590 tapes
===================

QEMU can expose an AWS tape image as a channel-attached IBM 3590 A50 tape
drive.  The device reports control-unit type/model ``3590/11`` and device
type/model ``3590/60``.  AWS record boundaries, multi-chunk records, tape
marks, forward and backward positioning, and block IDs are maintained by a
medium layer separate from the guest-visible 3590 command implementation.

The concise command line is::

  -dev3590 file=install.aws,devno=580

If ``devno`` is omitted, automatic allocation begins at ``0580``.

This creates a read-only raw backend by default.  ``readonly=off`` allows the
backend to be opened for writing.  An existing block node can instead be
attached with ``drive=NODE``.  Three- and four-digit hexadecimal device
numbers are accepted, so ``580`` and ``0580`` both select ``fe.0.0580``.

Some guests select a tape driver from the reported hardware identity.  The
optional ``ident`` parameter changes that compatibility identity while
retaining the AWS-backed 3590 command engine.  For example, Linux guests that
require a 3490 identity can use::

  -dev3590 file=tape.aws,devno=580,ident=3490

The accepted identities are ``3410``,
``3411``, ``3420``, ``3422``, ``3430``, ``3480``, ``3490``, ``3590``,
``8809``, ``9347``, and ``9348``.  The default is ``3590``.  The selected
profile controls the subchannel identity, Sense ID response, and identity
fields in Read Device Characteristics.  It does not change record limits or
enable the historical command set of the named drive.

The implemented commands cover Write, Write Tape Mark, Synchronize, Erase
Gap, Read IPL, NOP, Sense, Read Forward, Rewind, Read Previous, Rewind
Unload, Read Block ID, forward and backward block/file spacing, Locate, Read
Media Characteristics, Read Device Characteristics, Medium Sense, Mode Set,
Set Tape-Write Immediate, Sense ID, Set and Sense Path Group ID, Assign,
Unassign, Read Buffered Log and Load Display.  Read Buffered Log returns a
64-byte format-30 log with zero counters.  Load Display keeps the message the
drive would show, as long as its format control byte says (until the next
motion, the cartridge is removed or the drive is loaded); the QOM property
``display`` of the drive returns it, and the ``tape3590_display`` trace event
reports changes.  Mode Set takes tape-write-immediate and supervisor inhibit
(supervisor commands later in the same chain are rejected); the compaction
bit is accepted and has no effect.  The maximum logical record size is
256 KiB.  A CCW moves at most 65535 bytes, so Read and Write take larger
blocks through data chaining: the data of all CCWs of a data chain form one
block.

Forward and Backward Space Block present unit exception when they move over
a tape mark; Read Previous of a tape mark does too and leaves the position in
front of it.  Backward motion at load point is unit check with ERA 39, and a
read, spacing or Locate Block beyond the last block written is data check
with ERA 36 (end of data; locate failure in sense byte 1 for Locate Block).

Writing at the current logical position replaces that point and truncates the
old tail, including when writing a tape mark.  QEMU emits six-byte AWS headers
and splits records into chunks of at most 65535 bytes.  A failed write,
truncate, or flush fences the mounted volume so later modifying commands fail
predictably instead of continuing from an uncertain position.  Unload and
remount clears that fence after the image has been revalidated.  Running out
of room on the host is not such a failure (see below).

Volume size and end of tape
---------------------------

An AWS image has no fixed capacity: it grows as the guest writes.  The AWS
format does not limit it either (chunk headers hold only the 16-bit lengths
of the chunk and of the one before it).  What does limit a volume:

* The block ID the drive reports in Read Block ID and sense bytes 4-6 and
  locates by: a 32-bit logical block number on a 3590, so at most
  4294967295 blocks and tape marks per volume; 22 bits on the 3480 and 3490
  identities (bits 10-31 of their block ID), so at most 4194303.
* The optional ``capacity`` property, in bytes of AWS data, and the optional
  ``max-blocks`` property, which can lower the block limit (never raise it).
* The host: a full file system, a quota or the maximum file size.

The drive reports logical end of tape, the early warning of a real
cartridge, from ``eot-margin`` bytes or ``eot-margin-blocks`` blocks before
the first two limits on: Write, Write Tape Mark and Erase Gap still work but
end with unit exception, which tells the operating system to write its
trailer labels and continue on another volume.  The defaults are 128 MiB and
8192 blocks, at most an eighth of the limit: enough for the buffers an access
method may still have queued and the trailer labels.  A write that would pass
a limit, or for which the host has no room (``ENOSPC``, ``EFBIG``,
``EDQUOT``), is refused with unit check, equipment check, ERA 38 (physical end
of tape); nothing of the block is on the medium, the volume is not fenced, and
smaller writes that still fit work.  The host limits come without warning, so
leave room on the host or set ``capacity``.  Positioning back below the
early-warning point ends the unit exceptions.

Example: a cartridge of 800 MB, warning 16 MB before its end::

  -dev3590 file=scratch.aws,readonly=off,capacity=800M,eot-margin=16M

Runtime media changes
---------------------

A drive can start empty::

  -dev3590 id=tape0,devno=580

The standard removable-media QMP commands can then mount an AWS image::

  { "execute": "blockdev-add",
    "arguments": { "node-name": "tape-file", "driver": "file",
                   "filename": "install.aws" } }
  { "execute": "blockdev-add",
    "arguments": { "node-name": "tape-medium", "driver": "raw",
                   "read-only": true, "file": "tape-file" } }
  { "execute": "blockdev-insert-medium",
    "arguments": { "id": "tape0", "node-name": "tape-medium" } }
  { "execute": "blockdev-close-tray", "arguments": { "id": "tape0" } }

Use ``blockdev-open-tray`` followed by ``blockdev-remove-medium`` to unmount
it.  A media change resets tape position and raises device attention when the
subchannel is enabled.

The drive writes to a medium only when the medium is writable
(``read-only-mode`` of ``blockdev-change-medium``, ``read-only`` of the
node); a read-only medium is file protected.  This is decided at each mount,
so a drive can take writable and read-only media in any order.  While the
drive is unloaded it holds no permissions on its medium.

Rewind Unload rewinds and unloads the medium (the tray is then open, the
medium stays inserted until removed) and ends with unit check "unload
complete" (ERA 52; on the 3590 also reason code 3123, recovery action
"continue"), as the drives do.  A command chained to it is not executed.
Commands to the unloaded drive get intervention required (ERA 43).

IPL and CZAM recovery media
---------------------------

Select the tape with the operator-style IPL option::

  qemu-system-s390x -M s390-ccw-virtio \
    -dev3590 file=install.aws,devno=580 -ipl 580

The s390-ccw firmware executes the architected implied format-0 Read IPL CCW
at address zero; it does not use QEMU's ``-kernel`` loader.  Recovery media
for CZAM-only systems can use the first records as self-modifying Read IPL
channel programs before returning the final IPL PSW and loader.  Those
records are interpreted by the channel subsystem directly from the mounted
tape; QEMU does not scan for a private header or reconstruct the AWS image in
guest storage.

Migration
---------

The drive migrates with the medium position and drive state: the byte offset
of the next AWS header, the AWS data length, the logical block ID, the length
of the chunk before the position, the tray state, write-immediate mode, the
assigned partition and the volume fence.  Sense data, status and the channel
program are part of the subchannel state.  Channel programs run
synchronously, so no partially transferred record is in flight.

The medium itself is not migrated: the destination must mount the same AWS
image, from shared storage or copied by the management layer.  Loading the
state fails when the destination drive has no medium although a loaded tape
migrated, when a read-only medium differs in AWS data length from the
migrated one, or when the migrated position is not a block boundary of the
mounted medium (a record or tape-mark header whose backward link matches).
The position is checked when the VM starts running on the destination (or
after loading a snapshot), as reading the medium is not possible while the
state is loaded; if the check fails, the drive is presented unloaded (tray
open) and an error is logged.  A writable medium may still be written by the
source while the destination starts, so the destination does not parse it
at startup.  A drive whose tray
was open on the source stays open; closing it remounts the medium at load
point.
