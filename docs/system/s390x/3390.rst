Emulated 3390 ECKD disks
========================

QEMU can expose a plain CKD or CKD64 byte stream as an IBM 3390 ECKD disk on
an emulated 2107 control unit. The image engine accepts the uncompressed
Hercules-compatible ``CKD_P370`` and ``CKD_P064`` layouts. Compressed CCKD
and CCKD64 are intentionally not device formats.

The concise command line is::

  -dev3390 file=dosres.qcow2,format=qcow2,devno=200

The outer QEMU block backend may be raw, qcow2, or another block format; its
virtual byte stream must contain the plain CKD image. An existing backend can
instead be attached with::

  -dev3390 drive=dosres-node,devno=200

Three- and four-digit hexadecimal device numbers are accepted, so ``200`` and
``0200`` both select ``fe.0.0200``. Without ``devno``, 3390 disks are
allocated starting at ``0300``.

The supported geometry is 15 tracks per cylinder and up to 65,520 cylinders,
covering named 3390-1, 3390-2, 3390-3, 3390-9, 3390-27, and 3390-54 sizes.

Locate Record count and data orientations match the complete CCHHR search
argument against physical count fields on the selected track.  Data
orientation advances to the next count field in track order; CKD record
numbers are labels and need not be consecutive.

3380 disks
----------

Operating systems from before the 3390 often support only 3380 disks.  The
device has a 3380 identity: a 3380 on a 3990 storage control in Sense ID
(model X'02' for up to 886 cylinders, X'0A' up to 1772, X'1E' above: 3380
A/D/J, E and K) and the 3380 track format in Read Device Characteristics:
222 sectors, 47,968 bytes per track after home address and record zero
(1,088 bytes), track-capacity formula 1 with the factors 32, 492 and 236,
largest record 47,476 bytes.  Write Count, Key and Data keeps to that
capacity and ends with unit check, Invalid Track Format, when a record does
not fit.  The device accepts the same channel commands with either
identity.

A 3380 identity is selected by the image or by the ``device-type``
property:

* Images in the 3380 track format (header device type X'80', 47,616-byte
  track slots, as Hercules creates them for a 3380) are 3380 disks by
  default.  Such an image can only be a 3380.
* A 3390 image becomes a 3380 disk with ``device-type=0x3380``; its records
  then stay within the 3380 track capacity, so its tracks can later be
  copied to a 3380 image.

The control unit is a 3990 (model E9) for a 3380 and a 2107 (model E8) for
a 3390 unless ``control-unit-type`` and ``control-unit-model`` say
otherwise.  A 3880 control unit (``control-unit-type=0x3880`` with a
model) has no command information words: Sense ID then returns 7 bytes.

Hercules 3380 images with alternate cylinders (885 + 1, 1770 + 2 or 2655 + 3
cylinders) report the standard number of primary cylinders and the
alternate cylinder(s) in Read Device Characteristics; all cylinders stay
accessible.  Compressed Hercules images (CCKD, with or without shadow files)
are not a device format; Hercules' ``dasdcopy`` converts them, shadow files
merged, into the plain format::

  dasdcopy -o CKD base.dsk "sf=base_*.dsk" plain.ckd

Volume size
-----------

The image is a 512-byte device header followed by one 56,832-byte track slot
per track (47,616 bytes for 3380 tracks), so a 3390 volume of *n* cylinders
needs 512 + *n* × 852,480 bytes (3380: 512 + *n* × 714,240). The
number of cylinders comes from the header's 16-bit little-endian
``high_cylinder`` field at offset 18:

* If ``high_cylinder`` is nonzero, it is the number of cylinders (one-origin,
  1 to 65,520), whatever the file sequence byte at offset 17 holds: Hercules
  writes 0 there (or 1 in its old single-file form), zPDT-style images carry
  other values.
* If ``high_cylinder`` is zero and the file sequence byte is zero, the
  device's ``cylinders`` property gives the number of cylinders; without it,
  the volume size is derived from the backend length, which must then be
  exactly 512 + *n* × 852,480 bytes.

The backend may be longer than the volume needs: the bytes behind the last
cylinder are padding, which is never read as tracks, never written and never
shown to the guest. This allows block storage which rounds volume sizes up,
such as ZFS volumes, LVM logical volumes, or Ceph RBD images. A backend
shorter than the volume is refused. The header is never rewritten, so
truncating such a backend to 512 + *n* × 852,480 bytes gives the original
image back. Hercules itself requires the exact length, so the padding must
be cut off before an image is used with Hercules.

If the ``cylinders`` property is set and the header declares a different
count, the device is refused.

Hercules multi-file volumes are not supported. In a member of such a volume
the file sequence byte is the member's number (1 to *n*) and
``high_cylinder`` the zero-origin number of the member's last cylinder (zero
in the last member). Members are recognised and refused: the last member by
``high_cylinder`` = 0 with a nonzero sequence byte, later members by a first
track of a cylinder other than 0, and the first member by the formatted
track of the next cylinder right behind the cylinders its header declares.
For the same reason, an image whose cylinder count comes from the
``cylinders`` property is refused if a formatted track of the next cylinder
follows the last one.

Images should be created with ``high_cylinder`` set. Track slots which are
entirely zero read as empty tracks, so a new volume needs only the header::

  # 3390-3: 3,339 cylinders (0x0d0b), at least 2,846,431,232 bytes
  truncate -s 2715M dosres.ckd
  printf 'CKD_P064\x0f\0\0\0\0\xde\0\0\x90\0\x0b\x0d' |
      dd of=dosres.ckd conv=notrunc

The guest then initialises the volume, for example with ICKDSF or
``dasdfmt``. ``qemu-img ckdinit`` (see `Image creation`_) writes the
header, and by default an initialised empty volume, without this
arithmetic.

Unformatted tracks
------------------

A track slot that contains only zero bytes is presented as a freshly
initialised empty track: a home address with the slot's cylinder and head,
a standard record zero (key length 0, data length 8, zero data), and the
end-of-track marker. This is the layout Hercules uses for its CCKD null
track format 1 and the layout ICKDSF leaves on an initialised track. The
first write to the track stores the complete track in the slot. A slot which
is neither all zero nor a valid track is reported to the guest as an invalid
track.

Write durability
----------------

Like a real DASD control unit, which acknowledges a write once the data is in
its battery-backed nonvolatile storage, the device flushes its block backend
before it presents the final status of a channel program that wrote a track.
The guest can therefore rely on the data surviving a host crash once the
channel program has ended, also with ``cache=writeback`` or ``cache=none``.
If the flush fails, the channel program ends with unit check and equipment
check; the data is flushed again by the next channel program that writes.
Channel programs which only read do not flush. The flushes appear in the
``flush_operations`` and ``failed_flush_operations`` counters of
``query-blockstats``.

I/O, track cache and migration
------------------------------

Track reads, writes and the flush are asynchronous: a CCW that needs the
block backend runs in a coroutine and its channel program continues when the
I/O has completed, so a slow backend (network storage) does not stall the
vCPUs, and several volumes transfer in parallel. CCWs that work on the
current track (searches, reads of a track that is already in memory, Define
Extent, Locate Record) complete immediately.

The device keeps the current track in memory. The copy is dropped when the
device is reset and whenever the block backend is drained (block graph
changes, snapshots, ``stop``/``cont``, migration), so a reverted or replaced
image is read again. Writes by another process to an image in use are only
seen after such an event.

The device state (subchannel, Define Extent and Locate Record context,
orientation, reserve and path group) is migrated and saved with ``savevm``.
The drain before the state is saved lets the channel program in progress run
to its end; a channel program that is still waiting to start is migrated and
starts on the destination. The cached track is not migrated: the destination
reads it from the shared or mirrored image.

Image creation
--------------

``qemu-img ckdinit`` writes an empty 3390 volume into an existing image of
any format and protocol: a qcow2 or raw file, a block device such as a ZFS
volume or an LVM logical volume, or a network image given with
``--image-opts``. The image must hold at least 512 + *n* × 852,480 bytes;
anything behind the last cylinder stays padding. For example::

  qemu-img create -f qcow2 dosres.qcow2 2846431232
  qemu-img ckdinit -f qcow2 -m 3390-3 -V DOSRES dosres.qcow2

  qemu-img ckdinit -f raw -m 3390-9 -V SYSRS1 /dev/zvol/tank/vm-100-disk-1

By default the volume is *initialised* the way a minimal ICKDSF ``INIT``
leaves it, so that a stand-alone restore program or an operating system
accepts it as a volume:

* cylinder 0, head 0: record 0, the IPL bootstrap records ``IPL1`` and
  ``IPL2`` of a volume without IPL program (an IPL from it ends in a
  disabled wait with code X'0F') and the volume label ``VOL1`` (record 3)
  with the volume serial (``-V``), the owner (``--owner``, blank by
  default) and the address of the VTOC;
* the VTOC, by default at cylinder 0, head 1 for the 14 remaining tracks of
  cylinder 0 (ICKDSF's default for a 3390; ``--vtoc CYL,HEAD,TRACKS`` to
  place it elsewhere, below relative track 65,535): 50 DSCBs per track, a
  format-4 DSCB describing the volume and the VTOC, a format-5 DSCB
  listing the free space and format-0 DSCBs for the rest. The VTOC is not
  indexed. On volumes with more than 65,535 tracks (3390-9 and larger) the
  format-4 DSCB also marks the free space for the system to rebuild
  (DS4DOSBT), as these systems keep free space in other DSCBs there;
* all other tracks empty (all-zero slots, see below).

The volume serial has 1 to 6 characters A-Z, 0-9, the national characters
@, # and $, or hyphens. Without ``-m`` or ``-c`` the number of cylinders
comes from the image size, which must then be exact. ``--header-only``
writes only the device header, for a volume the guest initialises itself
(ICKDSF, ``dasdfmt``). ``--ckd`` writes a ``CKD_P370`` instead of a
``CKD_P064`` header; ``--serial`` sets the 12-character device serial
(random digits by default).

Everything after the header, padding included, is zeroed first (write
zeroes with unmap, which is cheap on qcow2, sparse files, thin pools and
ZFS); ``--no-zero`` skips that for a target known to read as zeros. The
header is written last. An image whose first track is already formatted
is only overwritten with ``--force``. Extended address volumes (more than
65,520 cylinders) are not supported, as the device does not support them.

Images can be exported for Hercules with ``qemu-img convert -O raw`` (cut
to the exact size).
