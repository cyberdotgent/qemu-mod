Emulated 3390 ECKD disks
========================

QEMU can expose a plain CKD or CKD64 byte stream as an IBM 3390 ECKD disk on
an emulated 2107 control unit. The image engine accepts the uncompressed
Hercules-compatible ``CKD_P370`` and ``CKD_P064`` layouts. Compressed CCKD
and CCKD64 are intentionally not device formats.

The concise command line is::

  -dev3390 file=dosres.qcow2,format=qcow2,devno=200

The outer QEMU block backend may be raw, qcow2, or another block format; its
virtual byte stream must contain the plain CKD image. An existing backend can
instead be attached with::

  -dev3390 drive=dosres-node,devno=200

Three- and four-digit hexadecimal device numbers are accepted, so ``200`` and
``0200`` both select ``fe.0.0200``. Without ``devno``, 3390 disks are
allocated starting at ``0300``.

The supported geometry is 15 tracks per cylinder and up to 65,520 cylinders,
covering named 3390-1, 3390-2, 3390-3, 3390-9, 3390-27, and 3390-54 sizes.

Locate Record count and data orientations match the complete CCHHR search
argument against physical count fields on the selected track.  Data
orientation advances to the next count field in track order; CKD record
numbers are labels and need not be consecutive.

Volume size
-----------

The image is a 512-byte device header followed by one 56,832-byte track slot
per track, so a volume of *n* cylinders needs 512 + *n* × 852,480 bytes. The
number of cylinders comes from the header's 16-bit little-endian
``high_cylinder`` field at offset 18:

* If ``high_cylinder`` is nonzero and the file sequence byte at offset 17 is
  zero, ``high_cylinder`` is the number of cylinders (one-origin, 1 to
  65,520). The backend may be longer than the volume needs; the trailing
  bytes are ignored and never written. This allows block storage which rounds
  volume sizes up, such as LVM logical volumes, ZFS volumes, or Ceph RBD
  images. A backend shorter than the volume is refused.
* If ``high_cylinder`` is zero, the volume size is derived from the backend
  length, which must be exactly 512 + *n* × 852,480 bytes.

This is the single-file form Hercules accepts: Hercules writes
``high_cylinder`` = 0 for a single-file volume, and also accepts a nonzero
``high_cylinder`` equal to the cylinder count. In a member of a multi-file
Hercules volume the file sequence byte is nonzero and ``high_cylinder`` is
the zero-origin number of the member's last cylinder; such members are
refused. Hercules itself requires the exact length, so trailing bytes must
be cut off before an image is used with Hercules.

Images should be created with ``high_cylinder`` set. Track slots which are
entirely zero read as empty tracks, so a new volume needs only the header::

  # 3390-3: 3,339 cylinders (0x0d0b), at least 2,846,431,232 bytes
  truncate -s 2715M dosres.ckd
  printf 'CKD_P064\x0f\0\0\0\0\xde\0\0\x90\0\x0b\x0d' |
      dd of=dosres.ckd conv=notrunc

The guest then initialises the volume, for example with ICKDSF or
``dasdfmt``.

Unformatted tracks
------------------

A track slot that contains only zero bytes is presented as a freshly
initialised empty track: a home address with the slot's cylinder and head,
a standard record zero (key length 0, data length 8, zero data), and the
end-of-track marker. This is the layout Hercules uses for its CCKD null
track format 1 and the layout ICKDSF leaves on an initialised track. The
first write to the track stores the complete track in the slot. A slot which
is neither all zero nor a valid track is reported to the guest as an invalid
track.

Write durability
----------------

Like a real DASD control unit, which acknowledges a write once the data is in
its battery-backed nonvolatile storage, the device flushes its block backend
before it presents the final status of a channel program that wrote a track.
The guest can therefore rely on the data surviving a host crash once the
channel program has ended, also with ``cache=writeback`` or ``cache=none``.
If the flush fails, the channel program ends with unit check and equipment
check; the data is flushed again by the next channel program that writes.
Channel programs which only read do not flush. The flushes appear in the
``flush_operations`` and ``failed_flush_operations`` counters of
``query-blockstats``.

I/O, track cache and migration
------------------------------

Track reads, writes and the flush are asynchronous: a CCW that needs the
block backend runs in a coroutine and its channel program continues when the
I/O has completed, so a slow backend (network storage) does not stall the
vCPUs, and several volumes transfer in parallel. CCWs that work on the
current track (searches, reads of a track that is already in memory, Define
Extent, Locate Record) complete immediately.

The device keeps the current track in memory. The copy is dropped when the
device is reset and whenever the block backend is drained (block graph
changes, snapshots, ``stop``/``cont``, migration), so a reverted or replaced
image is read again. Writes by another process to an image in use are only
seen after such an event.

The device state (subchannel, Define Extent and Locate Record context,
orientation, reserve and path group) is migrated and saved with ``savevm``.
The drain before the state is saved lets the channel program in progress run
to its end; a channel program that is still waiting to start is migrated and
starts on the destination. The cached track is not migrated: the destination
reads it from the shared or mirrored image.

Image creation
--------------

``work/ckd-qcow2-init.py`` in the source checkout is a dasdinit-like
development tool which creates a qcow2 container holding a preformatted
CKD64 image. For example::

  python3 work/ckd-qcow2-init.py dosres.qcow2 3390-3 DOSRES
  python3 work/ckd-qcow2-init.py archive.qcow2 3390-54 ARCHIV

Use ``--ckd`` for ``CKD_P370`` instead of the default ``CKD_P064``. Images
can be exported for Hercules with ``qemu-img convert -O raw``.
